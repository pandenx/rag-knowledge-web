## 1. 项目整体介绍

### 1 分钟精简版（背熟）

> 我做的项目是一套基于 RAG 的私有 PDF 文档知识库。用户上传 PDF 后，系统解析文档、分块、向量化存入向量库。用户提问时，系统检索文档相关片段，拼进提示词交给大模型，让大模型只基于文档回答，并展示原文引用。前端 React + TS，后端 NestJS + SQLite，向量库用 Chroma，调用豆包/通义千问的 LLM 和 Embedding API。

### 3 分钟详细版（讲清 RAG 链路）

> 项目分两条流程：
> **入库流程**：PDF 上传 → pdf-parse 提取文本 → 按块大小 500 字、重叠 100 字切分 → 每块调 Embedding 转成向量 → 连原文一起存入 Chroma 向量库。
> **问答流程**：用户提问 → 问题文本转成向量 → 在 Chroma 检索相似度最高的 3~5 个片段 → 拼进系统提示词（要求只基于文档回答，没有就说不知道，禁止编造）→ 发给大模型 → 通过 SSE 流式返回前端，逐字打字输出，同时展示引用的原文片段。

## 2. 技术选型理由

### 为什么用 Nest 而不是 Java？
> 我是前端背景，TS 技术栈熟练。Nest 和前端语言统一，能快速独立完成整套 AI 应用 Demo，聚焦验证 RAG 业务链路。同时我学习 SpringBoot 基础，理解 Java 后端开发思想，入职 Java 栈团队可以负责 BFF 层和 AI 交互模块，和后端同学协同开发。

### 为什么用 Chroma？
> 演示项目，Chroma 内嵌无需额外服务，开箱即用，开发成本低。生产环境可替换 Milvus / PGVector。

### 为什么用 SSE 而不是 WebSocket？
> AI 对话是服务端单向持续推流，SSE 基于 HTTP，实现简单、自动断线重连，适合"打字机逐字输出"场景；WebSocket 是双向全双工，本项目单向推流用 SSE 更合适。

---

## 3. RAG 完整链路原理

> RAG = 检索增强生成。核心：先检索相关资料，再让大模型基于资料回答。
> 为什么用：大模型不知道私有文档内容，直接问会"幻觉"编造；且大模型有上下文长度限制，塞不进整本几百页文档。所以先检索出相关片段，再喂给模型。
> 完整链路：文档入库（解析→分块→向量化→存库）+ 问答（问题向量化→检索→拼Prompt→生成）。

---

## 4. Chunk 分块策略、重叠窗口的作用

> 大模型上下文有限，长文档必须切片。块大小 500 字、重叠 100 字。
> 重叠窗口作用：防止一句话/知识点被切在边界上割裂，保证语义连贯，提高检索召回准确性。
> 分块是检索质量的命门：块太大浪费上下文且检索不精准，块太小语义不完整。需结合实际文档测试调优。

---

## 5. Embedding 与向量检索原理

> Embedding 把一段文字映射成一串数字向量，语义相近的文字向量距离更近。
> 向量库专门做向量相似度检索（余弦相似度），能实现语义匹配，而不是普通数据库的关键词匹配。
> 检索：把用户问题也转成向量，在向量库找距离最近的 TopN 片段。

---

## 6. 大模型幻觉问题，RAG 缓解手段

> 幻觉：大模型在没有依据时编造看似合理的虚假信息。
> RAG 缓解手段：
> 1. 只给模型提供检索到的真实文档片段，缩小回答范围
> 2. 系统提示词强制：只能基于参考文档回答，没有就说"无相关资料"，禁止编造
> 3. 引用溯源：展示回答依据的原文片段，用户可核对，倒逼模型不瞎编

---

## 7. SSE 流式实现、断线处理、长连接风险

> SSE（Server-Sent Events）基于 HTTP 单向持续推流，前端用 EventSource 接收。
> 实现：后端 @Sse()，LLM 开启 stream 流式返回，把每个 chunk 推到前端，前端逐字拼接渲染成打字机效果。
> 断线处理：监听客户端 close 事件，主动终止后端 LLM 请求，防止后台请求堆积和内存泄漏。
> 长连接风险：连接不释放会占资源；需正确管理连接生命周期、超时控制、连接数限制。

## 9. 项目瓶颈，可优化方向

> 如实回答，体现思考深度：
> 1. Chroma 适合演示，数据量大换 Milvus / PGVector
> 2. 仅支持 PDF 纯文本，可扩展图片、表格、多模态
> 3. 无用户权限系统，可扩展 RBAC 多租户
> 4. 未做分布式部署，适合中小文档量
> 5. 可加 Rerank 重排、Embedding 缓存减少 API 调用、分块策略自动调优
