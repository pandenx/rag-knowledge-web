# 项目开发规则（docs/rules.md）

> 用途：约束学习节奏、Bug 处理策略、规划机制，防止项目中途停滞或无限延期。

## 一、学习节奏规则

| 时段 | 学习/开发安排 |
| --- | --- |
| 工作日晚间 | 60~90 分钟编码开发 |
| 周末 | 2~3 小时整块时间，用于调试、整合、文档编写 |
| 疲惫降级日 | 最低保底 25 分钟，仅梳理文档、阅读源码，不写新代码 |

**硬底线**：不得连续断档 3 天。一旦连续 3 天完全不碰项目，强制回到"降级日"模式，用 25 分钟捡起来，避免整个计划停摆。

## 二、Bug 处理规则

- **单 Bug 攻坚上限 30 分钟**，超时则：
  1. 记录到 `error-log.md`（报错信息 + 排查过程 + 已尝试方案）
  2. 暂停该问题，次日再处理（或找人求助）
  3. 不要死磕一晚耗尽精力，导致后面几天放弃
- 每完成一个小功能，立即 `git commit` 提交，作为学习进度档案

## 三、每周规划机制（每周日执行，约 15 分钟）

1. 写下本周 **3 个可交付代码任务**
   - ❌ 禁止："学习 RAG 理论""看 Nest 文档"
   - ✅ 允许："实现 PDF 文本提取""完成 SSE 流式接口""接入 Chroma 向量库"
2. 预估每个任务耗时
3. 回顾上周 error-log，查看遗留 bug，判断是否需要本周修复

## 四、学习内容规则

- 学习目标始终**绑定在项目上**：遇到项目需要这个能力 → 去学 → 写进踩坑笔记 → 写代码落地
- 禁止先看完完整理论再动手；禁止漫无目的地刷技术短视频、公众号（信息消费 ≠ 学习）
- RAG 只学**应用层**，不深入机器学习、向量数学推导、模型训练/微调
- 同一时期只推进**一个项目**，不并行开多个 Demo

## 五、范围控制

- 严格执行 `project-plan.md` 中"附录 2 禁止新增功能清单"
- 项目未跑通核心 RAG 前，禁止添加花哨扩展功能（图片解析、Agent、权限系统等）
- Demo 追求"能跑、可演示"，代码可后续迭代，不追求企业级完美架构

## 六、节奏检查（每 4 周一次复盘）

自问 3 个问题：
1. 这个月新增了什么可运行功能？
2. 哪些知识点我可以口头讲清楚（模拟面试）？
3. 接下来 2 周的开发任务是什么？
